## 台湾商家的一天

以下是交给设计和开发的目标流程。店主只需要填写会改变本次业务结果的信息。平台负责维护授权、计算金额、记录状态，下一岗位从待办或订单继续办理。

| 阶段 | 谁、从哪里开始 | 本次操作和交接 | 做错、取消或中断时 |
|---|---|---|---|
| 1 开店 | 店主 → 注册或接受邀请 | 创建店铺，选中本店，进入工作台；有需要再补资料或邀请员工 | 中断后回到本店。跳过引导不会创建商品、库存、收款账户或寄件 |
| 2 准备商品 | 店主或获授权运营 → 商品 → 新增／导入 | 单件在同一编辑器填名称、规格、价格和可选期初库存。先存草稿，可售后再发布；批量先预览再确认 | 切页再回保留输入；有问题的批次返回错误行。响应未知先查原操作 |
| 3 决定如何交付 | 店主 → 设置 → 配送与运费 | 查看每种服务是否可用、固定运费及免运门槛；只改选中的服务。希望开通取付时才进入收款方式 | 没有服务、无法读取和没有权限各有对应提示。失败时其他服务、旧订单和历史费率保持原值 |
| 4 开卖 | 买家逛店；直播商家可从直播工作室选商品、开场 | 店面或直播认领均能进入购物车。商家能分清留言、认领、加入购物车和已下单 | 未连接平台只影响所需渠道。普通商品购买可沿店面继续 |
| 5 买家结账或商家代客下单 | 买家 → 购物车；获授权店员 → 创建订单 | 选数量、配送、门市或地址、付款方式，核对服务端报价再建单。买家和店员各自从岗位入口进入 | 改选门市后取消保留原选择；过期报价在提交前重读。只读查单链接不能覆盖购物身份 |
| 6 出货与收款 | 仓储 → 待发货 → 拣货 → 登记出货；收款人员核对代收 | 当前店和仓贯穿拣货与台账。手工寄件可记录单号；买家订单收到履约状态。收妥款另行登记，财务可核 | 缺库存不给成功回执。外部寄件结果未知查原单。发货、妥投和已收款各有自己的事实 |
| 7 买家查单、咨询或申请 | 买家 → 我的订单／单笔链接／联系商店 | 普通咨询进入商店询问；退货或取消进入订单待处理申请。买家能看到自己的申请状态 | 访客只见获准的一单，返回商品页可继续购物。可撤回的申请保留撤回入口 |
| 8 商家处理售后 | 有权岗位 → 待处理申请 → 详情 | 批准退货生成关联 RMA；拒绝保留原因。仓储收货、质检和处理库存后，符合条件的退款由有权人员单独确认 | 前置状态变化时重读。批准申请不产生退款，重复审批只产生一个业务结果 |
| 9 核账与次日工作 | 店主或财务 → 收款与报表；工作台显示尚需处理事项 | 按本店、币种和环境核对销售、收款、退款、代收及结算。平台订阅费用在账户账单里查看 | 无权或无数据给出不同结果。未到账的金额不能显示为到账 |
| 按需经营 | 店主或对应角色 → 团队、会员、渠道、网店、营销 | 调岗位、发布店面/回放、维护会员或开通渠道只在需要时办理；操作回到原业务对象 | 真实发送、广告、域名、供应商和订阅各按自己的授权及资格处理 |

## 哪些控件应该删、并、移或保留

| 原操作的负担 | 设计裁决 | 普通用户的验收 |
|---|---|---|
| 首件商品既在设置 3/3，又在商品中心；“跳过”还带有结束引导的含义 | **删除**设置里的首件表单及三步进度；复用商品列表的空态和普通新增入口 | 新店直接进工作台，第一件与第十件用相同编辑器。只改店铺资料时商品和库存零写入 |
| 只改一种运费，却进入开店/配送/收款组合向导，还看到环境、商店代号和密钥 | **拆开**日常运费、服务启用与可选外部连接。手工配送直接编辑当前服务；台湾手工首发移出供应商凭据 | 从设置识别本店服务、费用、免运门槛；保存后刷新，买家同车重新报价。普通路径不出现绿界表单 |
| 后台既有“创建订单”又在订单内建单，商品草稿、初始库存也有多个触发点 | **合并写入**同一命令，按工作场景保留有用快捷入口。入口选店及草稿相同 | 从两条入口能到同一表单。结果未知查看原命令，不能创建第二单或两笔期初入账 |
| 空状态统写“未配置”，收款摘要与详情给出相反指示 | **替换**为真实状态和当下能做的动作。无权、未开服务、读取失败和已保存分开 | 仓储能判断能否拣货，店主知道哪种配送启用，财务能按同笔订单核实款是否收妥 |
| 库存、建单、结算一起随大导航组显示或隐藏 | **按动作显示**。仓储可直接进自己有权的库存和台账；不能建单的岗位不显示建单；有权财务才见结算动作 | 以实际五种系统角色及两个授权门店从菜单进入，标题、数据、写入和回执属于同一店 |
| 看售后须先有退货单，联系商店只能提交，商家得猜去哪里找 | **补上交接**。订单下按买家申请排队，站内询问进收件匣。详情附订单及下一步 | 买家完成一笔合成申请或询问，商家无需链接、编号或后台查询，即能从队列找到并处理 |
| 改门市即擦掉原门市，切标签就清掉填了一半的申请 | **延后替换**到明确确认。在同店同身份内，看到、编辑与提交分为相应状态 | 取消回原门市，失焦回原输入。权限撤销或切店及时保护旧店内容 |
| 空店、日常店和技术人员看到相同导入、通知、集成、税务或故障信息 | **按需显示**。导入放商品；通知归店铺偏好；连接归渠道；多市场、税务及失败记录归获授权管理面 | 普通开店与接单可以独立走完，需要时有权用户仍能从所属模块查到和恢复 |
| 退款、库存调整、发布商品和发送消息有明确现实后果 | **保留必要确认**。确认页显示店、对象、数量/金额、可见性、动作结果；不为普通阅读添加确认 | 取消零写入，确认只产生一次结果。没有权限时服务端拒绝，界面没有虚假成功提示 |

**可用性验收**从登录后的正常菜单开始，让台湾店主、仓储和运营分别执行其任务，买家用独立会话。记录第一次选择、完成时间、退回/求助次数与刷新后的实际结果；提供直达 URL 或工程师口头提示的样本单列。上述次数和耗时目前没有真实人测基线。验收卡 TW14 记录原始结果，随后再设有根据的改进目标。

## 优先级与证据

1. **优先阻断错店和错误会话。** 两个已授权店的库存地址离线复核出现读错店；实际生产库存误写未证实。买家查单写入单笔只读凭据后，浏览器仍读到会话 active，继续读购物车却遭拒。保留原购物车与原单的入口须用同一浏览器复跑。见 `apps/admin/lib/backend.ts`、`apps/storefront/lib/buyer-server.ts` 和 `internal/buyerhttp/lookup.go`。
2. **让商家收到已经提交的工作。** 买家申请审批的 Go 命令和同事务建 RMA 已存在，欠缺商家 BFF、队列和能取到第 101 项的读端口。商店询问则已有 BFF，欠缺商家收件匣和处理控件。见 `internal/httpapi/return_requests.go`、`migrations/0221_buyer_return_requests.sql`、`internal/httpapi/contact.go` 与 `apps/admin/components/Inbox.tsx`。
3. **让状态读得准、改得回去。** 先保存明确的门市，再取消改选，原选择应保留；同一笔代收在详情、列表与财务应能对上。表单失焦返回、回放发布至店面、导入入口、无权财务操作分别依卡复验。已有商品草稿修复和已关闭转账的历史回执保留，各自只覆盖原场景。
4. **发布裁决。** 隔离环境验证错误前后状态和账，商家现场从正常菜单独立操作。未经本次验证的供应商、真实商家岗位和生产写入逐项记 NOT_RUN。业务代码、真实店配置和已签核设计的修改记录分别追踪。

原始现场依据为 `output/release-gate/5dffb337-ego-business-acceptance.md` 及 `output/release-gate/a2d079ca-ego-checkout-acceptance.md`。只读抽查商品操作发生于 2026-11-22 10:41 UTC，确认本店列表有“复制商品”和“库存台账”，当时没有可见导入入口。应用交付由原有项目 gate 和同一候选版本的证据裁决。
