# 台湾超商选店与跨境履约

2026-09-20，首发核心补充。用户已确认：**中国大陆或其他境外发货 → 台湾买家 → 7-ELEVEN/全家门市取货**。这是M13结账/M15物流/M22迁移的核心，不是可有可无的地址小组件。当前为研究与设计，未调用物流建单、回传客户SHOPLINE地址或修改生产订单。

## 1. 已知证据与不能推导的结论

- 用户截图展示7-ELEVEN公开电子地图，可按店名、店号、地区/路名选店；示例`281629`截图显示“興泰”。这是用户提供时点的公开店铺资料，不是跨境配送资格证明。
- 用户另给全家编号`017888`。全家公开查询页明确有6位店号、5位服务编号两种入口。保留原始字符串/来源，不去前导零、不截位、不按名称猜物流代码。[C02]
- 全家示例URL含`cvsname=FAMILYMART.SHOPLINEAPP.COM`和指向`message-center.shoplineapp.com/.../transfer/familymart`的`cvstemp`。这是现有平台的回传上下文，不是我们的商户申请、开发凭据或可复制回调。不得点击回传到客户现有订单。
- 普通门市查询、可回传的电子地图、真实承运商可配送门市、物流建单/标签、代收结算是不同能力。
- 公开资料中SHOPLINE“7-11跨境”、绿界“海外门市取货”常是**台湾发往海外**。不能因有“跨境”二字就认定支持大陆/海外入台湾。官方SHOPLINE出货说明列的是香港、新加坡等配送方向。[C08]
- 客户当前实际入台承运商、合同/接口、末端代码映射、是否COD/电子面单可迁移**尚未确认**；这是实施资格待办，不是功能设计做不到。

## 2. 方案比较与推荐

|方案|适配本场景|优点|代价/依赖|结论|
|---|---|---|---|---|
|A 接客户实际入台跨境承运商：选店/线路/建单/回调|最高，但需拿到有效合同和正式接口|复用已运行的境外揽收、清关、台湾末端、退件/代收责任链|确认服务商、账户归属、可外部平台调用、门市清单/编号及环境|**优先路径**；不能假定SHOPLINE合同自动可迁移|
|B 新签支持“境外→台湾、7-11/全家”的跨境服务商|条件适配|新站与旧平台解耦，有明确整链责任|两品牌、始发地、商品、温层、代收、退回和API必须逐项书面确认；开户联调不保证十天|A不可迁移时的候选；本轮不虚构已选供应商|
|C 先进口至台湾自有仓，再接绿界/蓝新等国内物流|只适合实际采用台湾仓+当地履约的业务|国内选店/面单/货态生态明确|多一段进口仓储与合同；改变当前履约方式，不应自动替用户决定|作为比较，不是本轮已选方案 [C03–07]|
|D 两家超商直接商务签约/技术接入|可评估，不等于公开地图即开放API|直接对接末端，能力/成本按协议|仍缺跨境头程/清关；多份合同与技术验收，公开页面不足以直接实施|有现成合同/量级和运维能力再选|
|E 复制公开地图页面或SHOPLINE回调|不适配|看上去省事|不能证明线路可达、订单映射与授权；回调可能写到旧系统；页面抓取易失效|**不采用**|

推荐理由≤3条：①选店结果必须真的可在客户线路出货；②复用正在使用的承运关系通常比新建清关/末端链风险更小，但需要合同确认；③选店UI归我们、门市和履约资格归授权服务商，日后换承运商不用重写整个结账。

体验建议：新站提供统一的“超商品牌 → 店号/店名/地区搜索 → 门市卡片确认”，支持最近使用门市与重新选择；有授权、可更新的门市目录时优先站内搜索，官方地图作另一路入口。不要自建一套靠爬虫维持的门市数据库。绿界官方确有门市清单API，可支持站内列表，但是否能用于本跨境合同必须先确认，不能借国内MerchantID泛用于别的承运业务。[C04]

## 3. 买家与商家的操作流程

### 买家结账

1. 国家/地区为台湾，购物车商品/尺寸/重量/温层符合已启用跨境线路后，展示“7-ELEVEN取货”“全家取货”；不可用时说明原因，不等付款后才发现无法出货。
2. 选择品牌后，可输入店号、店名或按地图/地区找门市；展示名称、地址、承运商可用状态与所选服务。手输店号是查询输入，不是直接合法地址。
3. 选择后自动回填**门市代码、店名、地址**，买家只需确认门市和自己的收件姓名/手机等必要信息；门市电话绝不能代替收件人手机号。
4. 门市资料以只读卡片展示，提供“更换门市”，避免买家手改成不存在的地址。授权后可保存常用门市，仍需每次结账重新检查可用性。
5. 计算该线路运费/税费/预计时效，显示实际支持的付款方式；**取货付款与在线已付款后店取分开**，不将超商代码缴费当成超商取货。
6. 提交订单再次核对购物车版本、线路/店号/费用；在线支付按PSP流程，COD按承运商代收合同，不因订单已成立就标已付款。

### 商家后台 / 客服代建单

- 商家自行启用已签约线路、品牌、取货付款开关、运费规则、寄件/退件资料；缺少正式资格不能用普通开关绕过。
- 客服侧栏/手工订单复用同一选店组件和后端验证，不要求客服复制地图地址；仍须订单权限、审计及买家确认流程。
- 出货前生成包裹、读取选店快照并再验门市/线路，建立跨境物流单及末端单号；获取标签/报关清单/追踪信息，未知建单结果先查询再处理。
- 若提供者只支持CSV/人工建单，可规划合规批量导出和导入回读；必须显式标为“人工履约”，经用户接受后才使用，不能冒充API全自动验收。

## 4. 适配器、数据与回填安全

以下是我们自己的设计，不声称第三方接口已按此实现。

### 4.1 最小职责

`PickupDirectory`：允许的门市/搜索/地区筛选/数据版本。

`PickupSelection`：发起选择、验证结果、存门市快照、重新选择。

`CrossBorderCarrier`：线路能力/报价、建运单、查询、面单/清关资料、轨迹、改店/取消/退回、COD对账。

三者在现有Go模块内实现并共用集成台账；不因此建立三个独立服务，也不因一个供应商返回店号就跳过线路检查。供应商密钥留服务器，店铺作用域由认证确认。

### 4.2 门市不是自由文本地址

|字段组|建议保留|约束|
|---|---|---|
|归属|tenant/store、cart或draft-order、selection session、revision|外部回调不能选择别的租户/订单|
|运输方向|origin_country、destination=TW、provider、service_code、contract_reference|显式区分入台/台湾国内/台湾出口|
|服务|超商品牌、温层、可配送地区、COD能力、末端B2C/C2C（如适用）|境外发货模式不等于末端交接模式|
|门市|provider_store_id、public_store_id/namespace（有证据才填）、原始代码、店名、地址、离岛信息（如提供）|全部字符串；供应商作用域隔离；不可假设6位/5位之间可计算转换|
|证据|selected_at、source、目录/规则版本、validated_at、门市快照|展示快照≠实时可用；出货前可能关转|
|收件人|符合线路要求的姓名/手机和必要清关联系资料|单独权限/保留期；不存到URL、日志或无关分析|
|订单物流|order/package ID、头程/末端运单、外部操作ID、状态版本|新旧系统ID只做映射，不把旧单重建收款|

### 4.3 官方地图跳转与回传

如选用绿界国内地图合同（仅作可验证的接口实例）：官方使用表单POST发起地图，以`ServerReplyURL`回传门市字段，`ExtraData`上限20字符；stage返回固定门市，不呈现真实交互地图。官方特别要求iOS不要另开新窗口、不要iframe，因此优先同页跳转并保留结账草稿。[C03]

我们的回填设计：

1. 服务端创建短期一次性随机selection session，绑定店铺、买家/客服授权、购物车revision、品牌、服务及允许返回页。透传字段长度服从所选协议；不塞买家明文或可猜order_id充当state。
2. 只向配置白名单中的官方地图发起，不接受用户提供任意callback/return URL。新站示意路径`/integrations/pickup/{provider}/return`是待实现路由，不是已部署地址。
3. 回传先做长度/字符/供应商/账户/品牌/服务/nonce/有效期校验。有签名的协议验签；**地图回填不一定有签名**，不能臆造CheckMacValue。绿界地图回传表未列该字段，物流建单/状态通知是另一份验签合同。
4. 回传只记录候选选店，不证明付款/买家身份、不直接创建物流单。恢复原站授权会话后，核对同一订单/购物车revision，再确认写入；不得因跨站POST缺cookie就全站关闭CSRF。
5. 服务端用授权目录/承运商验证结果重新核对店号、名称/地址和线路；不信任浏览器能任意填写的店名/地址。没有可用验证数据时拒绝标记`VERIFIED`，允许重新选店/人工核对但明确状态。
6. 重复回传幂等；过期/撤销/跨租户/旧revision拒绝；新选择发布后，迟到的旧回传不能覆盖新门市。失败保留原购物车，提供重试/换选店方式，不自动付款。

手机Safari、Android、Messenger内置浏览器分别测试。若内置浏览器限制cookie/跳转，提供明确“在系统浏览器继续”的恢复入口，并验证恢复票据与原购物车；不能承诺所有WebView无条件可用。

## 5. 跨境履约、COD与异常

建议订单关联多个运输阶段：`境外待交寄 → 已揽收 → 出口/运输 → 入台清关处理中 → 台湾分拨 → 到店待取 → 已取/未取退回`。这是统一展示模型，具体映射按承运商状态；不是假定每阶段都有API。

- 入台清关与超商选店分开。关务署说明进口快递的报关委任可通过EZ WAY等适用方式办理；实际是否适用、谁是进口人/报关责任方、需收集哪些资料，由所选线路与报关方确认。不能以门市地址替代进口人资料，也不能自动替顾客完成实名委任。[C09]
- 尺寸/重量/品类/温层/离岛/金额/COD能力按线路配置和最新合同，不能从普通地图上的“有这个店”推导可寄。未确认冷链就不展示为已支持。
- COD至少分“待代收、已取件代收、待承运商结算、已结算、差异/退回”，物流到店不等于收到商品款；手续费/汇率/退款与平台订阅收费分开对账。
- 关店/转店/服务终止：显示可行动错误，让买家/客服在允许状态重选；出货后是否能改店由承运商决定，不偷偷改库中地址后继续寄。
- 未取、拒收、清关失败、物流遗失、退款分别处理；不能照搬台湾国内某条“退回原寄件门市”的规则到境外商家。入台仓退件、境外退运、销毁和费用需要合同与商家确认。
- 跨境清关常有时间/费用不确定性，ETA注明来源/更新时间，不能以代码开发十天等同货物十天可送达。

## 7. 实施前需要的资料与当前推荐边界

需要客户/承运商提供：实际跨境物流商及合同账户主体；始发地→台湾的具体产品/服务代码；7-11与全家分别可用的目录/选店协议与编号映射；测试凭据和接口文档；建单/面单/轨迹/改店/退回/代收对账；收件/清关必需字段与用途；是否允许新独立站或多商家SaaS接入。

这不是要求重建物流链：优先核对原来在用的承运关系能否脱离SHOPLINE合法接入。没有资料前可以做供应商无关的UI/schema/mock合同测试，不能宣称两家超商已正式接通。不能用绿界/蓝新国内申请进度替代客户的跨境准入。

用户后续确认商家一般自带物流：不要求所有商家换成平台合同或通过平台下物流单。选店可交给其已签跨境服务使用，平台支持批量导出收货/门市资料、导入外部运单、通过经授权第三方API查件；但可达门市和代码映射仍要与真实线路一致。此BYO模式的字段/权限和买家查询见 [07第5节](07-双后台与多商户隔离.md)。
