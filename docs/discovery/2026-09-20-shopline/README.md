# 直播电商 SaaS：SHOPLINE 对标与开发需求补充

核验日期：2026-09-20（Asia/Shanghai）。状态：**需求/架构梳理，非产品交付；生产功能与性能均未验收**。

本补充是原《架构.md》与 R01–R22 的细化，不替换原始契约、不把原任务标成完成。用户已确认：**新独立站 xgdwm.com 承接商品和结账**，不能以链接跳回 SHOPLINE 代替交付。

## 已确认的目标

- 多商家 SaaS，不是单个 Page 的一次性脚本；优先解决 Facebook 直播评论关键词 → Messenger 发商品/预填购物车链接 → 新独立站结账。
- 商家自助经营：自己维护商品/SKU、价格库存、店铺首页装修、订单履约和营销。平台提供工具、模板和权限，不依赖我们逐店代配；平台运营台与商家后台分开。
- 首发买家以台湾为主，货物从中国大陆或其他境外发往台湾。7-ELEVEN/全家店号、店名、地图选店及回填是核心；按跨境承运商的台湾末端网络接入，不能拿台湾本地店到店或台湾出口服务冒充入台链路。
- 完整三端：平台管理后台、商家经营后台、买家独立站；商家通常自带物流，支持第三方API轨迹、外部运单登记及客户查件，收货地址/门市资料批量导出与运单回填。不是只交几个接口或强迫商家用平台物流。
- 会话分域：认证登录、独立站买家与商家聊天、Meta渠道会话、商家向平台求助分别处理。可以共用客服界面和订单侧栏，不能合并消息事实、身份或发送权限；Meta不可用不阻断站内售后。
- 约 10 天是用户期望的完整系统开发周期。本文保留全范围，给出排程及风险，不把它偷偷改成只交消息机器人，也不保证 Meta 审核与支付准入能在 10 天内通过。
- 按模块择优：吸收 SHOPLINE 已观察到的成熟业务流程；保留本项目有明确优势的设计；内部架构、吞吐和成本不可见的部分不能说对方更好或更差。
- **客户 SHOPLINE 后台是生产系统。** 本次不启停直播、不保存设置、不发消息、不创建订单/草稿、不改授权、不导出买家数据、不压测。正式迁移也必须安排独立测试与客户批准的切换窗口。

## 推荐结论

1. **用我们的交易与集成底座，加上 SHOPLINE 的操作流程。** Go 模块化单体、PG 唯一交易真源、River、严格隔离继续作为设计基线，不能宣称性能胜出。
2. **先贯通真实急需链路，再补齐全模块；不是删掉其余模块。** 工作室、自有店铺、支付订单、客服、权限和恢复是同一交付的依赖；广告/CAPI、物流深度能力、录像、会员等另列具体任务，未通过就如实记未完成。
3. **开发进度与外部准入双轨。** 第 1 天检查客户 App/主体/PSP 条件；功能开发可以用明确标注的 mock/sandbox 继续，正式营业必须通过真实门禁。
