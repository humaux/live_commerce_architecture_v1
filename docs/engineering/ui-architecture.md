## 0. 现状（盘点事实）

| | 商家后台 apps/admin | 买家前台 apps/storefront |
|---|---|---|
| 页面路由 | 23 | 16 |
| 组件 / 行数 | 42 / 16,231 | 29 / 6,019 |
| lib 文件 / 行数 | 71 / 12,896 | 41 / 8,483 |
| 文案文件 | 18 | 13 |
| CSS | 10 个文件 / 2,699 行 | 3 个文件 / 1,180 行 |
| 超过 800 行的组件 | SettingsWizard 2788、Ledger 1072、MerchantOrders 981 | OrderFlow 838 |

主要问题：
- 同一实体两处可改：商品名称、描述、价格、图片、归档在 ProductEditor 和 Ledger 里各有一套。
- 「新增商品」有 3 个入口。
- 后台金额格式化有 4 套，时间格式化有 8 处，其中 2 处写死 UTC；价格输入用最小货币单位。
- 导航文案来自 7 个文案模块。
- 3 个页面没有浏览器测试。
- 6 个组件在内部直接 fetch。
- 侧栏的渠道状态是写死的。

根因：没有 UI 层的统一模块。页面、组件、格式化、导航、权限、文案各自生长，也没有门禁约束「一个功能只有一个入口、一个实体只在一处编辑」。

- 一个功能只出现一次。
- 组可以折叠，侧栏可以滚动。

## 5. 代码模块化

### 5.1 分层

```
packages/
  ui/        设计令牌、基础组件、模式组件
             基础：Button Input Select Checkbox Switch Tabs Badge Dialog Drawer Toast Tooltip
             模式：PageHeader DataTable(选择+批量栏) FilterBar Pagination EmptyState ErrorState Skeleton SectionNav(sticky)
             表单：Field MoneyInput StockInput(∞) StoreDateTime ImageUploader(多选+排序)
  format/    金额解析与显示（TWD 整数元）、店铺时区时间、各域状态字典（唯一实现）
  i18n/      已有：Locale，加运行时 key 一致性检查
apps/admin/
  src/routes.ts      路由注册表（单一真源）：{id, path, group, labelKey, icon, permission, template, spec}
                     → 侧栏、面包屑、权限门、403、check-gates 都从这里生成
  src/shell/         布局：侧栏、顶栏、店铺切换、语言、AuthLayout、RoomLayout
  src/features/<域>/ orders products inventory live customers marketing store reports settings account
     pages/  components/  model.ts（纯函数）  api.ts（唯一调 BFF 的地方）  copy.ts（三语，typeof en）
  app/[locale]/**    只做路由入口：page.tsx 读权限，渲染 features/<域>/pages/*
apps/storefront/
  src/features/      catalog product cart checkout orders claim live content privacy
```

### 5.2 规则

1. 只有 `features/<域>/api.ts` 能调 BFF，组件不 fetch。
2. 金额和时间只能用 `packages/format`。组件里禁止直接用 `Intl.NumberFormat` 或 `toLocaleString`，禁止出现「最小货币单位」输入。
3. 每个实体只有一个编辑页。其它地方只能放跳转链接或只读展示。
4. 文案按域拆分，三语类型一致，运行时再检查一次。组件中不得出现硬编码的用户可见字符串。
5. 样式用设计令牌加按域的 CSS Modules，不再往全局 CSS 里加。
6. 页面模板固定为 7 种：ListPage、DetailPage、EditorPage、SettingsPage、WizardPage、WorkspacePage、ReportPage。新页面必须选一种。
7. 组件超过 500 行要拆，超过 800 行门禁失败。

### 5.3 BFF

`app/api/stores/[store]/[...resource]` 的白名单改成每个 feature 自带一张表，由路由注册表汇总。BFF 仍是唯一出口，前端不直连 Go。

## 6. 验收门禁（每个迁移批次都要过）

| 门禁 | 内容 |
|---|---|
| G-UI1 注册表一致性 | 每个路由都在注册表里，带权限、三语 labelKey 和浏览器 spec；导航中没有重复功能；check-gates 执行 |
| G-UI2 版式 | 每个页面在 1366×768、1586×992、2000×1100、375×812 下截图：无横向滚动、无元素重叠（Playwright 用 elementFromPoint 做重叠检查），截图交 K3 视觉 QA，P1 为 0 |
| G-UI3 格式 | lint 检查：组件中无 Intl 或 toLocaleString，无最小货币单位文案，无 UTC 显示；`packages/format` 有单元测试（TWD 整数元） |
| G-UI4 无障碍 | axe 无 serious 及以上；焦点顺序；按钮 44px |
| G-UI5 体量 | 组件 ≤800 行；fetch 只出现在 api.ts |
| G-UI6 视觉稿 | 每个域开发前先出视觉稿（三语，桌面加手机），owner 确认后才开发 |
| G-UI7 回归 | 现有全部浏览器模式和 release-gate B-* 保持绿 |

## 8. 已知局限与升级信号

- **主播端**：仍是网页，不做原生 App。升级信号：主播要求推流和直播间合一，或需要后台常驻提醒。
- **平台运营端**：仍是 CLI。升级信号：入驻商家超过约 10 家，或出现非技术运营人员。
- **工程结构**：单仓库两个 Next 应用。升级信号：前端多于 2 名开发并行，或页面超过 60 个，才考虑按端拆仓或引入组件文档站。

## 9. 不采用的方案

| 方案 | 原因 |
|---|---|
| 推倒重写 | 现有业务规则和门禁都绑在页面上，一次性重写风险高、周期长；逐域替换每步可验收 |
| 引入重型组件库（AntD、MUI） | 包体大，和现有设计令牌、三语、无障碍细节冲突；我们需要的是约 20 个组件的薄层 |
| SHOPLINE 式微前端（子域 iframe） | 平台级多团队方案，对我们是额外的部署和会话复杂度；实测还有 iframe 内语言不一致的问题 |


## 10. v2 修订（采纳网页 GPT 评审，2026-10-02）

来源：网页 ChatGPT（思考 10m44s），会话 6abf37a8。GPT 的意见是建议，不是证据：每条采纳项仍要经过门禁证明，未核实的外部事实另行标注。

### 10.1 使用端：按工作场景分端，而不是按应用分

仍然只部署两个应用（admin、storefront）。admin 内部分 5 种布局，共享组件和业务接口，但不共用一套塞满条件判断的页面。

| 端 | 用户 | 首期 | 形态 |
|---|---|---|---|
| 经营后台 | 店主、运营、财务 | P0 | admin 主布局（PC） |
| 移动任务视图 | 店主、临时处理订单的员工 | P0 只做高频任务：待办、查单、上下架、简单改价、连接异常 | 同一后台的响应式视图，不另建页面；规格矩阵、CSV、装修不要求在手机上完成 |
| 主播／场控工作台 | 主播、助播、场控 | P0 | admin 内独立布局（RoomLayout） |
| **出货工作台（新增）** | 仓库、打包员 | P0：出货队列、包裹、打印、交寄、异常；P1：扫码 | admin 内独立布局 |
| **客服／消息工作台（新增）** | 客服、直播助理 | P0：未认领、私信未送达、改收件信息、订单咨询、售后的最小闭环 | admin 内独立布局 |
| 买家前台 | 买家 | P0 | storefront |
| 入驻与身份 | 店主、员工 | P0，可断点续办 | admin 的 AuthLayout |
| 平台运营 | 平台方 | P0 用 CLI 并留审计；P1 做图形界面 | CLI |

两条边界：
1. 主播工作台管理 FB/IG 直播的商品和收单，不是开播工具。「暂停下单」「结束场次」不能暗示停止了 FB/IG 的视频直播。
2. 商家账号、买家身份、渠道消息、平台支持是四个不同的领域。消息工作台可以聚合网站消息和 Meta 消息，但不能凭同名、头像或昵称就认定是同一个买家。

### 10.2 一级导航（替换 §2 的分组；侧栏只放工作入口，所有可访问页面由注册表记录）

### 10.4 单一真源的含义（修订 §5.2 第 3 条）

多个入口本身不是问题，多套保存逻辑和规则才是问题：
- 每个实体的字段只归一个业务命令写入；入口可以有多个，但都调用同一个命令和同一个编辑组件。
- 新旧页面并存期间也只有一套权威写入，不能两边各写一份。
- 旧入口可以保留成跳转，旧的编辑逻辑必须下线。

### 10.5 模块化细则（修订 §5）

| 原方案 | v2 |
|---|---|
| packages/ui 约 20 个组件 | 分三层：基础视觉（ui）、后台模式（patterns）、业务组件（放在各 feature 里，例如退款面板不进通用 UI） |
| MoneyInput | P0。按主货币单位输入，内部精确转换；币种、允许精度、上下限都要显式给出 |
| StockInput(∞) | 「是否追踪」和数量是两个控件；∞ 只是辅助视觉，必须同时有文字说明 |
| format 含状态字典 | 拆开：format 只做格式化；状态码来自合同，状态文案归各领域的 i18n |
| 注册表单文件 | 每个域声明自己的路由，构建时汇总；Next 实际路由和注册表互相校验 |
| 注册表生成权限门 | 只用于界面体验（菜单可见、提示）；Go 仍要独立校验每次读写 |
| 只有 api.ts 调 BFF | 浏览器只走同源 BFF。服务端组件直接调用同一个 server-only 适配模块，不再用 HTTP 调本应用的路由。Route Handler 和 Server Action 都必须自行鉴权 |
| 组件超过 800 行失败 | 只作兜底；另加依赖方向检查、循环依赖检查（用依赖图工具，不只靠 ESLint no-restricted-imports，因为它挡不住动态导入） |

### 10.6 门禁补充（在 §6 之上）

- **依赖边界**：禁止跨 feature 深层导入，禁止循环依赖，业务域不得反向依赖页面。
- **网络入口**：业务组件里不得出现 fetch 或其他 HTTP 客户端。
- **批量操作**：服务端固定选择范围并再次校验；翻页后不得选错，失败项不得显示为成功。
- **交易恢复**：刷新、重试、返回、超时、断线、重复点击、并发编辑都不能造成重复下单、重复改库存、状态误报或数据丢失。
- **审计**：收款、退款、库存变更都要记录原因、操作人、前后值；日志和截图要脱敏。
- **视觉宽度**：增加 360、390、768、1024 以及断点附近的宽度；覆盖长英文、长商品名、大金额、错误、加载中、无权限、批量栏、软键盘弹出。复杂表格在手机上允许表格内横向滚动。
- **视觉判定方式**：AI 视觉 QA 只是辅助，「无重叠、可点击」要用 DOM 几何检查和真实点击来判定。截图基准纳入版本控制并经人审查。
- **真实环境**：FB/IG 内置浏览器要用真机测试，不能只靠设备模拟（首期固定 6 类测试环境）。
- **触控目标**：主播端和买家端 44–48 CSS px 是产品要求，不写成 WCAG AA 的最低线。

### 10.7 迁移顺序（替换 §7；否决「后台全部改完才动前台」）

| 阶段 | 范围 | 核心验收 |
|---|---|---|
| 止血包 | 金额输入、UTC 误显示、按钮不可点、写死的渠道状态、重复的编辑逻辑 | 输入 50 显示并保存为 50 元；没有假的连接状态；关键操作都能点到 |
| W0 外壳与契约 | 布局、路由注册、权限、格式化、BFF 适配层、错误模型、店铺作用域；保存旧版截图基线 | 路由全覆盖；角色和跨店铺负例；三语和时区契约 |
| W1 商品与库存纵切 | 商品编辑、库存命令，同时改前台的商品展示、规格和金额 | 新建、复制、改价、调库存后前后台一致；历史订单不被改写 |
| W2 普通购买闭环 | 购物车、结账、选店、货到付款和转账、商家订单、买家订单状态 | 刷新、返回、重复提交都不会重复建单；选店可恢复；付款和履约状态正确 |
| W3 直播收单闭环 | 渠道、场次、主播工作台、留言收单、私信、认领、客服异常入口 | 重复事件不重复加购；链接预览不算认领；发送失败可追踪；断线恢复不漏状态 |
| W4 交付与资金闭环 | 出货、打印、交寄、物流异常、未取退回、售后、收款对账、有条件的发票 | 建单不等于交寄；退款不自动回库；代收不等于到账；部分失败可处理 |
| W5 经营增强 | 优惠、装修、页面和菜单、顾客增强、高级报表、导入增强；广告后置 | 发布可回滚；导入有预检和逐项结果 |

正式营业的门槛是各 P0 闭环都完成，不是做到 W3「能接单」就放量。

历史金额：不能整库乘以 100。要按版本、操作记录和业务证据判断哪些记录来自错误的输入语义，再逐条修复。（试点目前只有 1 个商品，修复成本很低。）
