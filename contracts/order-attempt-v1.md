## 1. Transaction feasibility and choice

**All local order effects can share one physical PG connection and transaction. Different pool logins are an authority/API obstacle, not a reason to commit between domains.** No provider call is needed to create the local pay entry, entered CVS destination, hold or order.

| Option | Feasibility and decision |
|---|---|
| A. SECURITY DEFINER composition | **Recommend.** One Go-owned execution `pgx.Tx` invokes narrow domain-owned definers; a composite final-write function may orchestrate SQL. Retain pure Go pricing/template/encryption in the owning admission/execution Tx (§2). A literal all-SQL function would duplicate/port that logic and is not the recommendation. All order effects have one commit. |
| B. One connection with controlled role switching | PG supports `SET LOCAL ROLE`, but current startup checks reject mixed runtime memberships and require `session_user = current_user`. Granting buyer/checkout roles to merchant runtime would broaden authority and break those checks. Reject for this unit; do not relax them. |
| C. Preserve separate cart/quote/destination/Begin/receipt commits | Technically possible only with a durable step ledger, replay and compensation for each step. No unavoidable local boundary justifies this complexity. Reject for new attempts; use bounded reconciliation only for legacy data (§5). |

Add family guard `ops.guard_order_attempt_job` and deferred link trigger `ops.check_order_attempt_job_link`: validate exact args, permitted producer/worker lane, and matching stored attempt/generation for C1 and sweeper re-enqueue; never let a job create admission authority. Resolve outbox/order/version from the operation's durable DB mapping before domain locks; do not add outbox/generation fields to the pinned job args. Dispatch versus reconcile comes from paired DB state/lease, never a mutable job argument. Logs/metrics contain opaque IDs, fixed codes and durations, never frozen plans, contacts, provider payloads, bearer URLs/tokens or request bodies. Queue inspection/retry must not become another PII store.

All tables enforce tenant/store RLS from verified authentication; worker/definer paths re-establish a validated attempt scope. Browser roles have no direct writes. Tenant-wide key lookup first checks principal/store/family ownership: another principal/store's key receives the **same non-disclosing `idempotency_conflict`** as any unusable key, with no attempt/order/scope data or reason identifying another owner. **Admission CAS:** the server returns the current scope ID/generation and its attempt/terminal reference. An explicit new-order action submits `expected_scope_id`, `expected_generation` plus the last terminal reference (or initial generation zero), a new transport key and canonical request. The expected ID is a CAS token, not authentication authority: compare it to the server-resolved scope. Under the scope lock, allocate generation `expected_generation + 1` and commit C1. A stale scope/generation gets `intent_conflict` even if the winner settled or the scope retired. New generation requires the previous attempt terminal; storage loss, `none`, 404, elapsed time or no pending row does not authorize it. Clients must not automatically advance after mount/conflict/recovery. This serializes one staff principal/store, not the store; other principals still obey bundle locks.

Within the retention period, exact same key/body replays its attempt in **any state** before fresh placement validation; different body is always `idempotency_conflict`. After retention purge, deny the old scope/generation rather than return a receipt or treat it as never admitted (§3). Canonical hashing includes endpoint family, target bundles/conversation, each claim origin, delivery/payment choice and request schema; credential rotation must not change key lookup. Persist the original buyer owner at admission, including server-created private owners where needed; never guess a linked customer from a social label or capability. Old key versions may authenticate credentials but cannot redefine order ownership.

**Scope — owner decided 2026-10-13:** one scope per **principal + store**, shared by manual/for-buyer ordering. This deliberately serializes that staff member's different buyers and tabs; a stalled intent can block them until the bounded deadline/sweep. It prevents cross-entry duplicates without guessing buyer identity. Per-target scope is not part of v1. Other principals remain concurrent and bundle ownership still fences duplicates.

**Frozen plan lifetime.** C1 records `admitted_at` from the database and **`execute_by = admitted_at + 15 minutes`**, never extended by retries. Retain each AEAD key version while any PENDING/quarantined legacy plan references it; key retirement checks those references. Temporary key-service failure is retryable. A definitively missing/unusable plan key settles a new-protocol PENDING as ABORTED(PLAN_UNAVAILABLE) under its zero-effects fence. Legacy partials instead use §5 reconciliation; missing decryption is not absence proof. Delete plan/contact ciphertext on settlement, retaining the minimal receipt. No bearer credentials are in terminal receipts.

## 3. State, locking and recovery

```text
not admitted -- C1 + generation CAS --> PENDING -- C2 --> COMMITTED
                                         \-- fenced zero-effects decision --> ABORTED
```

`UNKNOWN` is a transport observation, never a fourth authoritative state. Terminal states never regress or change order identity. `COMMITTED` means the complete **local** pipeline is durable, including a definitive notification disposition; it does not mean paid or delivered.

| Transition / operation | Authority and rule |
|---|---|
| Admit | Current merchant authentication, CSRF and placement permissions (including catalog, inventory and orders; claims/message permissions where requested), server generation CAS. No order effects. |
| Execute/resume PENDING | Internal executor's durable admission grant plus frozen plan; current read authentication controls disclosure, not the ability of a queued worker to finish. Do not call ordinary `Place` and repeat its mutable permission/option gates. Integrity, inventory and explicit erasure/cancel fences remain mandatory. |
| Commit | The complete C2 write set and receipt become visible together. Receipt records the initial notification planning disposition/outbox ID; current delivery status is separate. Message authorization/window/privacy loss yields VOID/not_sent, not a permanently PENDING order. |
| Abort/seal | Under the same fence, prove no committed C2 order/resources and prevent the old executor from committing; then persist reason and terminal receipt. A 422/409, missing receipt, credential error or failed lookup alone is not absence proof. |
| Recover/read | Primary, uncached lookup by attempt ID or original key across **all states**. PENDING invokes/schedules the same frozen executor; terminal replies use receipt/pointer, not the encrypted body. Recovery transport keys never create an order or select a different intent. |
| Cancel an order | Attempt remains COMMITTED; current order state becomes CANCELLED. Release/refund follows existing order rules. In the same cancellation Tx revoke collection credential and void READY notifications (§4). |

### 3.1 Fence and lock sites

**C2's first locking statement is attempt `FOR UPDATE`, followed by a PENDING + exact generation/owner/subject-binding recheck.** A terminal row returns its receipt without effects; a stale generation cannot execute. Inline and River run the identical path: the loser waits, rechecks and becomes a no-op replay. Neither a read lease nor a prior read of PENDING grants permission to write.

There are two admission/erasure prefixes, then a shared domain order. Acquire all IDs within a level in sorted order; identifier discovery is an unlocked, non-authoritative read followed by recheck under locks:

- C1: subject-admission advisory barriers for **every indexed subject** → scope row → new attempt → owner/domain admission reads. Subject membership is immutable after C1; if authoritative resolution changes the set, roll back and reacquire the complete sorted set, never append an earlier barrier. No C2 effects occur here.
- Erasure: the same sorted subject barriers (prevent concurrent C1 for those subjects) → all affected attempt rows, sorted → owners, sorted → domain order. Re-scan/recheck bindings before redaction. This replaces the old owner-before-attempt erase path; private-owner plans are discovered through §2's subject index.
- C2: attempt first → owners → claims/bundles/grants → parcel groups → order serialization keys/rows → attempt cart/quote → catalog/SKUs → delivery service heads → pickup/destination heads → inventory balances → pay entries → conversation/takeover state → integration bindings → outbox → integration operations → notification enqueue. Preallocated new order keys use the same order-level serialization as existing orders. The fresh `river_expiry` job is inserted inside Begin **before the order row**, as required by its dependency; it is not a late notification job or an inversion of existing-row locks.
- Order-only commands (cancel, copy, rotation, reminder, C3/C4, notification sweep) enter at parcel group/order and follow the same suffix. They never acquire an attempt/scope/owner lock later. **C2 never locks or updates scope or subject barriers**, including through helpers/triggers; C1 alone advances the scope generation. FKs to immutable existing scope/subject rows must introduce no reverse lock dependency. Erasure never acquires scope after attempts.

### 3.2 Deadline, sweeper and error classification

The existing main River worker hosts periodic **`OrderAttemptSweep`**, every 30 seconds and once on startup, discovering at most 100 oldest PENDING IDs per batch **without locks**. Process each in its own Tx: take that single attempt `FOR UPDATE SKIP LOCKED`, recheck state/generation/deadline, then follow the owner/domain suffix. The batch is a scheduling bound, not a multi-row lock set; never hold one attempt's owner while acquiring the next attempt. For a row before `execute_by`, ensure one live same-attempt/generation execution job; a missing, completed, discarded or retry-exhausted job is re-enqueued with `InsertTx`. A live job's state does not extend the deadline. At/after `execute_by`, settle **ABORTED(EXPIRED)**, release admission reservations/unused grants and fence queued workers in one Tx. C2 checks `clock_timestamp()` against the deadline after acquiring its fence and immediately before its terminal write; crossing it rolls back its entire write set. Keep existing transaction/statement budgets; no timeout increase is part of this design.

**Absence proof:** for the new protocol only, a locked PENDING row proves zero committed C2 effects, since all such effects and COMMITTED share one transaction. A sweeper waiting on C2 either sees COMMITTED or acquires a still-PENDING zero-effects row. A lost commit acknowledgement must first re-read that authoritative row, never infer absence from the connection error. Legacy partials are not admitted into this proof.

Sweep heartbeat and oldest-overdue-PENDING age are monitored; missing two sweeps or an overdue row alerts with fixed codes/IDs. Under available PG and a running periodic worker, discarded jobs and persistent executor defects therefore cannot strand the scope indefinitely. During database/worker outage the fence remains closed; no unsafe wall-clock deletion substitutes for the sweep.

Classification is by SQLSTATE **and typed domain code/stage**, never text substring. The same table governs inline, River and recovery:

| Result | Before C1 | Fenced new-protocol C2 / notification |
|---|---|---|
| `40001`, `40P01`, `55P03`, `57014`; `08xxx`, `57P01`–`57P03`, connection loss/unknown commit | No success claim; read key authority on retry | Roll back/re-read; keep PENDING if still PENDING, retry with bounded backoff until `execute_by`; unknown commit cannot abort. |
| `PT400` invalid request | NOT_ACCEPTED for this fresh call | Required plan invalid → ABORTED(PLAN_INVALID); notification format invalid → VOID. |
| `PT401` authentication; `PT403` authorization | Refuse this call without settling an earlier attempt | Ordinary placement auth must not recur. Known erased/closed-subject safety denial → ABORTED; message authorization denial → VOID. Unexpected helper/auth invariant → retryable internal fault, alert, deadline sweep. |
| `PT402` insufficient stock/funds for an admitted local resource | NOT_ACCEPTED with stable code | ABORTED(insufficient_inventory/resource_unavailable), zero effects. No external charge occurs in C2. |
| `PT404` scoped resource missing | Non-disclosing NOT_ACCEPTED | Required SKU/owner/service gone → ABORTED(resource_unavailable); notification conversation/binding gone → VOID. A failed owner resolution in **legacy** recovery stays quarantined. |
| `PT409` idempotency/intent/body or bundle ownership conflict | Exact replay or typed conflict; never admit a second intent | Re-read fence; replay terminal or reject stale caller. Another intent's bundle → ABORTED(bundle_reserved/bundle_order_exists). `retry_later` retries PENDING. Message `window_closed`, `capability`, `takeover_changed`, `duplicate_recent` → VOID. ## 4. Pay entry and payment notification

Three separate facts: **orders** authorize collection; **pay entry + link_version** authorize a credential; **business outbox** records a notification. Neither a River job nor an integration-operation status substitutes for all three.

- **Copy = read.** Read the existing order-scoped pay entry under the order lock; never call regeneration. **Owner-decided absolute lifetime is 72 hours:** each credential version expires at the earlier of the payment deadline or **72 hours after that version's first issuance**. Copy and reminders never extend it. After expiry, the merchant must explicitly CAS-rotate to a newly issued version (§4); old versions remain expired/revoked and the order's payment deadline is never extended. Exchange grants at most **15 minutes**, capped by remaining entry lifetime, and authorizes only that order's payment, never a profile/cart/other orders. Revalidate payable/erasure/version on every exchange and payment action. Preserve old links through §5's adapter, not by resetting old redemption/expiry.
- **Reminder = new notification intent.** Unique semantic identity is `(tenant_id, store_id, order_id, link_version, kind, client_reminder_key)`. Additionally bind `(tenant_id, store_id, order_id, kind, client_reminder_key)` across **all versions/states** to the authenticated principal and canonical request hash; replay that record before reading the current version. Thus response loss or rotation cannot turn the same key into a second send. A deliberate second reminder needs an explicit action/new client key, existing messaging permissions/window/rate checks and a new row; UNKNOWN never automatically supplies that action. Batch admission freezes its selected order IDs; child keys derive from `(batch_intent_id, order_id)`, not loop time or buyer PII. Persist exact `order_id` even for checkout reminders; buyer A's row never blocks buyer B's order.
- **Rotation = explicit CAS revoke.** Require `expected_link_version`, explain that previously sent URLs stop working, serialize on the order, issue one new version and revoke the old credential/VOID its READY notifications in the same Tx. Never silently requeue. **Only DISPATCHING blocks routine rotation**; ACCEPTED/DELIVERY_UNKNOWN permit an explicit confirmed CAS rotation while preserving the old send evidence. Neither confirmation nor rotation resends an uncertain operation. Existing `inventory:reserve` + `orders:read` authorize routine manual-link management; add scoped **`orders:link:revoke` + `orders:read`** for security revocation, with exact permission-catalog/ACL tests in implementation. Security revocation may invalidate even an in-flight credential but cannot claim the remote message was recalled. Audit actor/store/order, fixed reason, old/new version, affected outbox IDs and time; never URLs or contact data. System order cancellation follows its existing permission checks and performs the same invalidation atomically.
- **Disclosure is proved, not guessed.** Return `buyer_link` only after confirming under the order lock its exact committed credential/version, payable state and permitted disclosure. Return null for CANCELLED, erased, `window_closed`, `link_unavailable` or any not-established path; never retain a pre-lock candidate in an error result. Validity is established at the read's serialization point, not promised forever after another actor cancels.
- The UI does not offer a regenerating copy for queued/planned sends or `link_unavailable`; it displays queued/reminder-in-flight. A real read-only copy may be exposed when the server can return the same established entry. No hidden rotation fallback.

**Bearer security surface.** A forwarded link may reveal only merchant display name, opaque order reference, amount/currency, payment deadline and permitted payment methods. Do not expose buyer name/email/phone/address, customer history, chat or tracking; richer views require separate buyer authentication. Preserve PG lookup limits from `0094_merchant_tools.sql:171–196`: 10/IP, 5/order and 200/store per 10 minutes, fail closed, with non-disclosing invalid/expired responses. Apply them at credential exchange, not static asset load. Use no-store, no-referrer, token-redacted access logs and no third-party analytics on bearer pages. Reusable redemption must issue **order-only** authority, not the existing full-owner capability. Independent **security_reviewer sign-off on expiry, forwarding/PII, limits, key custody and old-link cutover is required before implementation acceptance**; these limits are contract requirements, not optional owner decisions.

**Worker key custody is an explicit new requirement.** `cmd/claims-worker` C2 needs the versioned plan AEAD ring, a dedicated order-only pay-entry encryption/signing ring, and the send-preparation keys: existing `COMMERCE_META_PAYLOAD_ACTIVE_KEY_ID`/`COMMERCE_META_PAYLOAD_KEYS_JSON` and `COMMERCE_META_PAGE_HPKE_ACTIVE_KEY_ID`/`COMMERCE_META_PAGE_HPKE_PUBLIC_KEYS_JSON`. The first two rings are new order-attempt/pay-entry namespaces, not a grant of `COMMERCE_BUYER_BFF_KEY` or full buyer authority to the worker. Current worker startup forbids the payload ring (`cmd/claims-worker/main.go:108–109`); implementation must explicitly amend that custody check for this executor, not assume it already has the keys. Security review must sign off API/worker provisioning, least key access, missing-key startup failure, version retention/rotation, environment/log redaction and key-isolation tests. Keys stay in secret configuration, never River args or receipts.

Outbox record: tenant/store/order/attempt (attempt nullable for later reminders), immutable semantic key, kind, `link_version`, encrypted destination/payload, nullable binding/operation references, worker generation, state, `void_stage` and dispatch/outcome evidence. Order/version are mandatory for every payment-DM producer. A **refused-before-dispatch plan is outbox VOID with `operation_id = NULL` and no notification job**, including a store with no binding; retain only the fixed refusal code and minimal audit fields, not an unnecessary recipient payload. Do not fabricate a binding or job to satisfy `integration.operations`. All dispatchable plans have one unique operation and its `external_operation_v1` job, created atomically in C2's final notification-planning stage. C3 claims both in one Tx; C4 records both outcomes in one Tx.

Enforce **`CHECK (operation_id IS NOT NULL OR (state = 'VOID' AND void_stage = 'before_c3' AND dispatch_authorized_at IS NULL))`**. Both `state` and `void_stage` are NOT NULL fixed enums (`void_stage`: `none`, `before_c3`, `after_c3`), so SQL UNKNOWN cannot bypass this CHECK. `dispatch_authorized_at` is set by C3 and can never be cleared. The definer refuses unlinking an existing operation: VOID after planning/authorization retains its operation and evidence. Thus NULL is allowed only for a plan refused before C3, never READY, DISPATCHING, ACCEPTED or DELIVERY_UNKNOWN. Nullable binding is likewise permitted only for the unbound refused plan. Notification commands, operator actions, sweeps and reconciliation use this mapping:

| Outbox ↔ external operation | Allowed transition / evidence |
|---|---|
| VOID ↔ (none) | Refused plan before C3: `operation_id NULL`, no notification job, definitive not_sent. It is terminal and cannot be promoted to READY; a later notification requires a new explicit intent. |
| READY ↔ READY | Created together. Domain job repair may requeue the **same** ready intent after revalidation. |
| DISPATCHING ↔ DISPATCHING | C3 CAS, lease and generation persisted together; only the winning invocation gets one dispatch permit. |
| ACCEPTED ↔ SUCCEEDED | C4/reconciliation with provider acceptance evidence; immutable accepted disposition. |
| DELIVERY_UNKNOWN ↔ UNKNOWN or ACKNOWLEDGED | Ambiguous outcome, async acknowledgement or expired lease. Reconcile/query only; acknowledgement without acceptance proof is not success. |
| VOID ↔ CANCELLED | Operator cancel, order cancel or rotation wins **before** authorization; atomically invalidate READY send authority. |
| VOID ↔ BLOCKED_POLICY | Policy/consent/window refusal before C3, or definitive no-effect evidence; post-C3 mere policy loss leaves UNKNOWN. |

| VOID ↔ FAILED_FINAL | Exact-generation authoritative no-effect terminal failure. No reopen of this payment-DM operation. |
| Any other pair | Fail closed, no HTTP or buyer-link disclosure from that inconsistent path; quarantine for fenced repair, never guess one side from River status. |

When an operation exists, every arrow writes both records in **one transaction**, including operation-API paths. VOID↔(none) writes only the terminal outbox/refusal disposition in C2; operation APIs cannot address it. Operator `cancel` is allowed only for READY and means VOID/CANCELLED together. Generic external-operation **`retry` is forbidden for all payment-DM states**, including READY repair and VOID/FAILED_FINAL reopen; return typed `not_retryable`. Existing registry already excludes `meta.dm_send` FAILED_FINAL reopen (`external-operation-v1.md:153–171`); retain that restriction and close generic READY requeue bypasses. Query/reconcile remains allowed under existing quotas and the paired fence. A new resend is a new §4 reminder intent, with fresh business authorization, not a reset of either state machine.

Main River periodic **`PaymentDMLeaseSweep`**, every 30 seconds and on startup, discovers expired DISPATCHING IDs without locks, then processes one notification per Tx in §3's order/conversation/binding/outbox/operation sequence (never hold an operation while discovering/locking another order). Recheck lease/generation, invalidate the old lease, and atomically set **DELIVERY_UNKNOWN / UNKNOWN**, retaining the consumed dispatch permit. Enqueue **`external_operation_v1` with exactly `{operation_id, version: 1}`** only when existing query budget/backoff permits; UNKNOWN state authorizes reconciliation only, without adding a mode argument. Otherwise keep UNKNOWN with its next eligible time/operator-visible exhausted-budget reason, not VOID. Never renew dispatch authority. This runs even when the original job was discarded. Later matching provider acceptance evidence may reconcile to ACCEPTED/SUCCEEDED, but a stale completion token cannot overwrite the new generation. Monitor missing sweeps/expired leases; do not leave DISPATCHING forever waiting for another claim.

```text
READY -- locked authorization/CAS --> DISPATCHING --> ACCEPTED
  |                                      |-------> DELIVERY_UNKNOWN
  \---------------> VOID                 \-------> VOID (proven not sent)
```

Before C3, lock the order and outbox in §3 order; revalidate payable state, privacy, consent/window/binding/message authority, current credential/version and worker generation. If invalid, VOID without HTTP. C3 commits DISPATCHING with a single-use dispatch generation; only the invocation that wins READY→DISPATCHING may perform its one HTTP call. Seeing an existing DISPATCHING row is never a resumable send permit. Provider I/O occurs outside PG. A lost acknowledgement or crash after authorization (including before I/O) is DELIVERY_UNKNOWN unless the operation adapter proves no send occurred. Never automatically resend it or allocate a new semantic key. ACCEPTED means provider acceptance, not buyer delivery. Outcome commits are generation-fenced; late evidence may refine UNKNOWN to ACCEPTED but cannot trigger another send. Duplicate River delivery cannot authorize a second provider call.

Cancel atomically revokes the pay entry and voids **READY** rows. Guarantee: cancel committed before dispatch authorization ⇒ **zero provider calls**. If dispatch authorization won, a remote send may already be in flight; preserve DISPATCHING/UNKNOWN/ACCEPTED evidence and make the link unpayable. Do not claim remote exactly-once or recall. Current `0129_lc_b6_order_for_buyer.sql:521–611`, `0144_checkout_reminders.sql:165–184` and `internal/integrations/core/dispatcher.go:303,365–370,472–491` lack this complete authorization boundary; a lock-free pre-send check is insufficient.
